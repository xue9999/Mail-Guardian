# Daily application backup

`backup.py INSTANCE` is an explicitly installed root maintenance job. It does
not change mail, upload files, delete retained generations or enable a timer.
The worker checks mail every fifteen minutes after the operator enables its
timer; systemd and the existing worker lock prevent overlapping mailbox runs.

The backup holds the existing migration lock exclusively and then the helper
lock. An active worker makes backup fail visibly rather than capturing changing
state. After checking the stack and storage, the job briefly stops Rspamd to
exclude its independent model updates. It makes a WAL-aware standalone SQLite
copy, checks its integrity and strict readiness, copies the encrypted archive
tree, configuration, three application credentials and installed release. It
decrypts every referenced archive with the original archive identity and checks
its complete message hash, then forces a fresh Redis RDB export. It resumes
Rspamd and encrypts the immutable
copy with `guardian-recovery seal-directory`.

The backup encrypts the original archive identity *inside* the payload. The
distinct backup decryption identity stays on the Mac or in independent custody;
only its public recipient is needed by the VPS. This is an application recovery
generation. It does not restore the Ubuntu installation, reconcile mail that
changed after the generation, prove a working restore or constitute an off-host
copy by itself.

Provision `/etc/mail-guardian/INSTANCE/backup-recipient` as a root-owned 0600
regular file containing the public `age1...` recipient generated by:

```sh
guardian-recovery keygen --identity-file NEW_PRIVATE_KEY --recipient-file NEW_RECIPIENT
```

Keep `NEW_PRIVATE_KEY` away from the VPS. Preserve it separately from the
ciphertext copies and test decryption before relying on the backup.

After installing the reviewed release, an administrator can install the optional
job without enabling it:

```sh
sudo install -o root -g root -m 0755 /opt/mail-guardian/current/backup.py /usr/local/libexec/mail-guardian-backup
sudo install -o root -g root -m 0644 /opt/mail-guardian/current/mail-guardian-backup@.service /etc/systemd/system/
sudo install -o root -g root -m 0644 /opt/mail-guardian/current/mail-guardian-backup@.timer /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl start mail-guardian-backup@pilot.service
```

Completed generations are root-only files under
`/var/backups/mail-guardian/INSTANCE/`: `TIMESTAMP.age` and
`TIMESTAMP.age.sha256`. Copy **both** to the Mac over pinned SSH when available.
Retain the checksum separately with the recovery records; it detects a changed
download but is not an external signature or freshness proof. A generation is
complete only when its checksum sidecar exists. The job keeps old generations;
capacity must be reviewed before adding a deletion policy.

An isolated restore uses the retained checksum, a new private destination and
the backup identity:

```sh
guardian-recovery open-bundle --source GENERATION.age --destination NEW_PRIVATE_DIRECTORY \
  --identity-file BACKUP_IDENTITY --sha256 RETAINED_SHA256
```

Verify the database, encrypted archives with the original identity, and Redis
model in an isolated target before enabling the backup timer:

```sh
sudo systemctl enable --now mail-guardian-backup@pilot.timer
```

The timer runs daily around 03:07 server time and catches up after downtime.
The service retries failures every fifteen minutes, including a busy worker.
Failed captures publish no completed generation. Normal errors resume Rspamd
in a `finally` block. If the backup process is killed, root-only incomplete
staging can remain, and the next regular worker's `up` operation starts the
scanner again. Never treat a retained staging directory as a completed backup.
Backup failures appear in systemd/journal; external alert delivery remains a
separate configuration step.
